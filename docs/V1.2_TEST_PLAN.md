# Solara V1.2 Manual Test Plan

_Last reviewed: 2026-07-15_

This plan covers live weather, OAuth, real calendar and notification behavior, and multi-device flows that credential-free CI cannot prove.
The automated suite covers pure engine logic, normalization, routine filtering, cloud calculations, and the onboarding browser smoke flow.

**Legend:** 🟢 covered by the current automated or credential-free browser suite · 🟡 requires a controlled manual check · 🔴 blocked on an external service or credential.

---

## P0 — Forecast consolidation

- 🟢 Dashboard renders activity cards from the shared `fetchForecast`.
- 🟡 **Dashboard ↔ Calendar agree.** Open Dashboard, note an activity's safe window; switch to
  Calendar tab — the same activity's window should match (same forecast, no double-fetch).
- 🟡 **Switching location re-fetches.** Change the active location; both views update; no stale data.
- 🟡 **Offline/slow:** kill network, reload — you should see the "Could not load weather" error with
  a Retry, not a blank screen.

## P2 — Weekday/weekend routines

- 🟢 An activity restricted to **Weekdays** shows a "Weekdays" chip on its card.
- 🟡 **Routine filters the plan.** Set an activity to Weekends only. In **Plan Ahead**, confirm it
  only appears on Sat/Sun, and a Weekdays-only activity never lands on a weekend day.
- 🟡 **Edit modal round-trips.** Open Edit → toggle individual day chips → "Weekdays"/"Weekends"
  presets set the right chips → Save → reopen and the selection persisted.
- 🟡 **All-seven = every day.** Select all 7 days (or none); the chip disappears and it plans every day.
- 🔴 **Notification respects routine** (needs FCM live): a Weekends-only activity should not be the subject of a weekday morning push.
  Follow [DEPLOYMENT.md](./DEPLOYMENT.md#notification-activation) and section 5 of [GO_LIVE.md](./GO_LIVE.md#5-notification-verification).

## P3 — Cloud sensitivity

- 🟢 Edit modal shows the "Account for cloud cover" toggle; persists.
- 🟡 **The label appears when it should.** This needs a genuinely cloudy, high-UV forecast, so it
  won't always trigger. To force it: pick a city that's currently overcast with UV above your
  activity's max (or temporarily lower the activity's Base safe UV). A window that only qualifies
  because of cloud should show **"☁ Safe under cloud"**, and its reported Peak UV should still be
  the _true_ (un-discounted) value.
- 🟡 **Conservative by design:** a clear-sky high-UV hour must NOT be marked safe. Confirm cloud
  sensitivity never green-lights full sun.
- 🟡 **Off by default:** a brand-new activity has cloud sensitivity off and behaves exactly as before.

## P4 — Multi-location

- 🟢 Popover shows pinned active location, a saved shortcut with remove (✕), the "n/limit saved"
  counter, and a ☆ Save affordance when the active location isn't yet saved.
- 🟡 **Save → switch → remove flow.** Add a city (saves a shortcut), switch to it (active updates +
  weather refetches), remove a shortcut, confirm the counter updates.
- 🟡 **Tier gating.** As Free (3) vs Pro (12): at the limit the ☆ Save / add is blocked with an
  upgrade hint; switching the active location still always works (never gated).
- 🟡 **"Use my location"** updates the active location but does **not** auto-save it as a shortcut.
- 🟡 **Persistence.** Saved locations survive a reload (localStorage), and sync to Firestore when
  signed in.

## P1 — Calendar scheduling (🔴 blocked on OAuth provisioning)

Can't be tested until you create a Google OAuth client ID and set
`NEXT_PUBLIC_GOOGLE_OAUTH_CLIENT_ID` (see DEPLOYMENT.md). Once live:

- 🔴 Connect calendar → grant consent → "Recommended" slot reflects real busy blocks.
- 🔴 "Book this time" writes an event whose description carries the flexible start range.
- 🔴 freeBusy privacy: only busy _times_ are read, never event titles.
